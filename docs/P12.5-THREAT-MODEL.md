# P12.5-THREAT-MODEL.md — Modelo de Ameaças

> Fase **P12.5-00**. Lista mínima de ameaças que a implementação demo/E2E deve
> mitigar, com o controle correspondente. Cada controle é verificado por teste
> (unit) ou por asserção de segurança (P12.5-13).

## 2. Análise por categoria

### Anonymous Demo

- Acesso via `/demo` com `ExecutionContext { tenantId: "__demo__", actorType: "human", authMode: "anonymous-demo" }`.
- Desligamento imediato: `PUBLIC_DEMO_ENABLED=false`.
- Controles: rate limits, session TTL, budgets, permissões restritas.

### Tenant Isolation

- `__demo__`, `__e2e__` e tenant real são contextos distintos.
- **Nunca** `anonymous → authenticated real user`.
- QA Agent (`__qa_agent__`) opera em `__e2e__`, nunca no tenant real.

### Evidence

- Evidence Pack com metadata (runId/scenarioId/commitSha) + artifacts (screenshots/traces).
- Metadata → storage; artifacts → object storage (retention aplicada).
- Nunca secrets/dados pessoais nos artifacts (redaction).

## 3. Suposições

- Demo NÃO acessa Supabase real (dados demo = fixtures isoladas) → T5 mitigado por design.
- QA Agent NÃO edita código (P12.5-08); Fix Agent edita SOMENTE dentro do workflow controlado (P12.5-10).
- Sem auto-merge, sem auto-deploy, sem Level 4.
- Graph/Neo4j não são ampliados nesta fase (P12.5-08 §8).

## 4. Aceitação de risco

- Model comparison da P12 declarou `insufficient_evidence` — mesma honestidade aqui: sem evidência suficiente, classificação = `unknown`/`low confidence → manual review`.
- E2E local em CI é propenso a flakiness → retries 2 no Playwright + repeat no regression loop.
