Comece por aqui

O que é o MilesControl?

É um projeto web de gestão de milhas aéreas. Mas o que você vai ver aqui não é o app: é o processo por trás dele — o workflow que garante que toda mudança seja testada, revisada e rastreável antes de chegar à produção.

📦

Uma ideia entra

Uma nova funcionalidade, um bug para corrigir ou uma melhoria. Tudo começa com uma tarefa classificada em uma categoria.

⚙️

Gates verificam

No caminho, 4 portões (gates) checam intenção, consistência, autorização e evidência. Se algo faltar, o fluxo para — de propósito.

📤

Entrega sai

Com tudo validado, a mudança vira um Pull Request revisado por um subagente especializado e segue para produção com rastro completo.

A jornada

De ideia a entrega, passo a passo

Clique em cada etapa para ver o que acontece e qual telemetria fica registrada. As etapas em verde já foram concluídas na prática; em vermelho, o que acontece se você pular uma delas.

🚀

Sessão começa rule-26

Toda sessão de trabalho inicia com npm run session:start. O sistema registra um marcador de tempo e carrega o contexto da última sessão (handoff).

{"type":"session:start","description":"sessão iniciada","branch":"feat/minha-mudanca"} 📄 docs/handoff.md atualizado automaticamente
▾
🗂️

Categoria da tarefa docs certos

Cada tarefa tem uma categoria (feature, bugfix, docs, refactor, chore). Ela define quais documentos o agente deve ler — sem leitura desnecessária.

feature → WORKFLOW.md + CONVENTIONS.md bugfix → DEBUG.md + CONVENTIONS.md docs → apenas AGENTS.md
▾
🧠

INTENT Gate rule-33

Antes de qualquer edição, o agente declara: "o código faz X; o teste espera Y; a spec diz Z". Se os três não baterem, ele não edita — reporta.

INTENT: código faz X; teste espera Y; spec diz Z → se divergirem: NÃO editar, reportar
▾
🔁

TWINS Check rule-34

Ao corrigir um bug, o agente busca o mesmo padrão no projeto todo e corrige todas as ocorrências — não só a que apareceu.

TWINS: searched <padrão> — found N locais
▾
🎯

Decisão estratégica rule-27/28

Features passam por um Conselho de LLMs (5 perspectivas + síntese) com veredito em docs/council/. Refactors exigem uma spec técnica.

feature → council-to-superpowers → docs/council/veredito refactor → spec técnica em docs/superpowers/specs/
▾
🛠️

Codificação por subagente rule-39

A implementação é executada por um subagente especializado (coder). Ao concluir, um evento coding:done com a marca subagent:true é registrado — é a evidência do gate.

{"type":"coding:done","description":"Codificação por subagente concluída", "branch":"chore/code-review-gate","subagent":true, "skill":"subagent-driven-development"}
▾
🔎

Code Review por subagente rule-38

Antes do PR, um subagente revisor audita o diff de forma independente (read-only), com veredito explícito. O evento code-review:done prova que a revisão aconteceu.

{"type":"code-review:done","description":"Review aprovado por subagente", "branch":"chore/code-review-gate","subagent":true, "verdict":"approved","skill":"requesting-code-review"}
▾
🧪

Testes + Build quality

Testes unitários, build e verificação de docs rodam. A nota de qualidade (outcome grade) é registrada — o padrão mínimo é 80%.

✅ 503 testes · 56 arquivos 📊 outcome grade: 100% (206 vezes) · 80% (62) · 60% (6)
▾
🛂

Pre-pr: 39 regras telemetria

O npm run pre-pr valida 39 regras automáticas + gera um relatório HTML. Cada execução fica registrada no events.jsonl. Falhou? Mensagem acionável diz exatamente o que fazer.

🔍 PRE-PR CHECK — 39 regras ✅ relatório: docs/reports/<data>/PR<n>-*.html 📡 eventos: pre-pr (324) · rule:fail (205) · healed (23)
▾
🔐

AUTH Gate rule-35

Push, merge e deploy são irreversíveis. Por isso, exigem a palavra exata do usuário ("manda bala", "autorizo"...). Sem a citação, o agente não age.

AUTH: usuário disse "<citação exata>" → sem citação: não agir
▾
📤

PR → review → merge

O Pull Request nasce com relatório anexado, os checks de CI rodam (check-pr, e2e-smoke, Vercel) e, aprovado, é mergeado na main.

branch → PR (base: main) → checks CI → merge → deploy
▾
🏁

Sessão encerra rule-26

npm run session:end registra o evento final, atualiza o handoff e preserva o contexto para a próxima sessão.

{"type":"session:end","description":"sessão encerrada"} 📄 handoff.md salvo para a próxima sessão
▾
🚫

E se eu pular um gate? fail-closed

Os gates são fail-closed: sem evidência, o pre-pr falha (exit 1) e mostra a mensagem de como corrigir. Não dá para "empurrar com a barriga" — o sistema prefere parar a liberar.

❌ rule-38: nenhum evento code-review:done na branch feat/x Dica: node scripts/event-log.mjs code-review:done \ "Review aprovado por subagente" --meta '{"subagent":true}'
▾

Os portões

4 gates que protegem a entrega

Cada gate tem uma pergunta simples. Se a resposta for "não", o fluxo para — e o sistema diz como destravar.

🧠INTENT Gate

Pergunta: o código, o teste e a spec contam a mesma história?
Como funciona: antes de editar, o agente declara os três em uma frase. Se divergirem, reporta em vez de editar.

rule-33 fail-closed

🔁TWINS Check

Pergunta: o bug existe em outro lugar do projeto?
Como funciona: ao corrigir, o agente varre o código buscando o mesmo padrão e corrige todas as ocorrências.

rule-34 fail-closed

🔐AUTH Gate

Pergunta: o usuário autorizou com as palavras exatas?
Como funciona: push/merge/deploy exigem citação literal do usuário. Sem ela, nenhuma ação irreversível.

rule-35 bloqueia ação

🛂Evidence Gates

Pergunta: a codificação e a revisão foram feitas por subagentes?
Como funciona: eventos coding:done e code-review:done com subagent:true na branch são exigidos antes do PR.

rule-38 + rule-39 fail-closed

🎯Council / Spec

Pergunta: a decisão estratégica foi debatida?
Como funciona: features passam por conselho de LLMs (5 visões + síntese); refactors exigem spec técnica versionada.

rule-27 / rule-28 por categoria

🤖RTK ativo

Pergunta: a análise estrutural de código está disponível?
Como funciona: extensão .pi/extensions/rtk.ts versionada + binário ≥ 0.23.0 garantem auditorias por Tree-sitter.

rule-37 fail-open
